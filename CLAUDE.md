# Working rules for this repo (read every session)

This project converts HL7 v2 patient data into Australian AU Core FHIR and proves conformance
with the official HL7 validator. Correctness is decided by the validator and the published
spec, never by memory or by what looks right.

## Pinned versions
All versions live in `versions.toml`: FHIR 4.0.1, AU Core 2.0.0, AU Base 6.0.0, HL7 validator
7.0.2, Synthea v3.4.0 and its seed. Never change a version anywhere else.

## Read the spec locally
The pinned packages are in `~/.fhir/packages/<name>#<version>/package/`. For any question about
a profile, slice, cardinality, system URI or invariant, read the StructureDefinition JSON there
(e.g. `hl7.fhir.au.core#2.0.0/package/StructureDefinition-au-core-patient.json`), and the official
examples in `.../package/example/`. Do not answer from memory.

## Never invent
- No FHIR system URIs, codes, value sets or identifiers that are not in the package files or the
  rules files. If you cannot find one, stop and say so.
- No real identifiers or patient data, ever. Fixtures are synthetic and generated by
  `scripts/make_fixtures.py` from a fixed seed. Scale data comes from Synthea via
  `scripts/generate_population.py` into `data/` (generated, never committed).
- The exporter never alters clinical content: no unit conversion, no invented reference ranges,
  abnormal flags or panel codes.

## Tests are a contract
- Never edit `fixtures/expectations.yaml`, a golden fixture or a test's expected value to make a
  test pass. Those change only when the spec says so, and the commit message must say which rule.
- New fixtures need an entry in `fixtures/expectations.yaml` (a test enforces this).
- After any change to ingest, mapping or rules, run `make test` and `make validate` and report the
  error diff, not just pass/fail. Changes that could affect volume, linking or detection also need
  `make scale` (which includes the faulted population: 100% detection, 0 false alarms).
- The validator is never mocked in integration tests.

## Module boundaries
- `gateway/ingest/` knows file formats (HL7 v2), nothing about FHIR. `patient_adapter.py` reads
  ADT, `lab_adapter.py` reads ORU^R01, `dates.py` converts HL7 dates without inventing precision
  or timezones. Repeated segments are located as `OBX(2)-5` (2nd OBX, field 5).
  Files are read as UTF-8; any other encoding is `ingest.bad-encoding`, never guessed. MLLP
  framing characters are transport, not content, and are removed before parsing.
- `gateway/model/canonical.py` is the only shape passed between ingest and mapping.
- `gateway/mapping/` builds FHIR and the trace; it never decides validity and never repairs bad
  data (a bad IHI is emitted as received so the validator reports it). `patient_builder.py` and
  `observation_builder.py` build resources; `trace.py` maps validator expressions back to HL7
  fields for every resource type; `fhir_json.py` writes decimals with the digits as received
  (`2.80` stays `2.80`): always write resources with its `dumps`, never `json.dumps`.
- An OBX status or coding system missing from the rules file is `mapping.unmapped-code`, never a guess.
- `gateway/validate/` runs the official validator and categorises issues by message id.
- `gateway/pipeline.py` routes messages by type and links each lab report to a registered patient
  (IHI, then MRN, then Medicare). No match is an error (`link.orphan-result`); a match with a
  different name or birth date is a warning (`link.demographic-mismatch`), never an error.
  Every result becomes an Observation; results with an ingest error are not converted. Small runs
  validate every Observation; large runs validate every result shape plus a deterministic sample
  (`ObservationSelection`), and the report says which.
- Field positions and code translations per sender live in `gateway/mapping/rules/<source>.yaml`.
  Rules translate only codes the sender actually sent: no defaults for a blank field (no
  invented country, name type or address type).
- Record ids are file stem + MSH-10 and unique in a run (a missing or repeated control id is
  flagged and the line number decides). Observation ids use the OBX occurrence, never OBX-1.
- A value the gateway cannot represent faithfully (e.g. a multi-part OBX-5) is an ingest error,
  never truncated.
- `gateway/identifiers/` holds check-digit algorithms (IHI, Medicare, LOINC Mod 10). Each is tested
  against published examples; never change one without a published source.
- `scripts/inject_faults.py` breaks a seeded share of a feed and writes a ledger (`faults.json`).
  Each fault type's expected issue must be one its hand-written fixture already proves
  (`tests/unit/test_faults.py` enforces this). `gateway/faults.py` scores a run against the
  ledger: found only with the right id at the right field. Never loosen that to raise a rate.
- `gateway/examples.py` checks a run's built-in examples (fixtures/) against
  `fixtures/expectations.yaml` with the integration tests' exact rule, and their results are
  always validated, whatever the sample. The dashboard shows that check; it never decides it.
- `gateway/store.py` records every run in `out/history.db`. After a change, `python -m gateway diff`
  lists findings that appeared or were resolved; report that diff, not just pass/fail.
- `gateway/dashboard/` only displays the report: no pass/fail logic, no re-deriving categories or
  locations. Plain-language issue labels live in `LABELS` in `build.py`; the glossary and
  explanatory text live in `template.html` and must stay accurate to the spec and the code (no
  claims the report doesn't support). The page is written for non-technical readers;
  developer detail goes behind the "Technical detail" switch (`.tech`). After changing
  `template.html`, the inspector's or the monitor's `page.html`, build the page (for the dashboard, run
  `python scripts/check_dashboard.py` on it) and look at it in both themes and at phone width.
- `gateway/inspector/` is the Message Inspector: a static page that runs the unchanged gateway in
  the browser (Pyodide, pinned in `versions.toml`). `bridge.py` adds display data only (lines,
  decimal-safe resources, JSON path -> HL7 field from the builders' traces) and never decides
  anything. The official validator cannot run there and the page never implies it did: recorded
  findings are shown only for unchanged built-in examples, from a report with no package
  substitutions. `scripts/check_inspector.py` must show Pyodide output identical to the command line.
- `gateway/interface/` is the live-interface layer: `session.py` processes one message at a time
  through the unchanged pipeline (validator off) and remembers accepted registrations so lab
  reports can link; `ack.py` builds HL7 v2.4 ACKs (MSA-1 from table 0008 only: AA, AE, AR);
  `mllp.py` is a local MLLP listener and sender, bound to 127.0.0.1 by default and only ever for
  synthetic data. An ACK reflects the gateway's own checks, never the official validator.
- `gateway/monitor/` is the Interface Monitor: a static page that replays a synthetic feed through
  `Session` on Pyodide. Its feed always carries one planted message per fault type the gateway's
  own checks catch (from the fault ledger) and one unsupported message type, marked "planted";
  every other message must be clean. Staged message faults come from `fixtures/faults/` (plus the
  same unsupported example); network faults are simulated in the page and labelled so.
  `scripts/check_monitor.py` must show every ACK identical to the command line and the feed's
  planted/clean promise kept.
- `gateway/site.py` is the site's one layout and palette (black and white; colour only for meaning:
  error, warning, pass, couldn't check): header (site pages, current page marked, links
  leaving the site marked, a light/dark button that follows the device until chosen), the "On this page" bar with page controls, and footer (incl. the legal
  notices). Every page fills its placeholders from it; never give a page its own header, nav or
  footer. Each page has one h1, one `<main id="main">`, and an `id` for every section it lists.
  Problems shown in code use its `hl-error`/`hl-warning` (field) and `ln-error`/`ln-warning` (line)
  classes on every page: red for an error, amber for a warning.
- `gateway/provenance.py` says where a page's data came from: generated feeds carry `source.json`
  (written by `scripts/generate_population.py`, kept by `inject_faults.py`), fixtures are described
  from `fixtures/`, and the pipeline stores the result in the report (`data_sources`). Every page's
  "Where this data comes from" table is rendered from it; an input with no record of its origin is
  said to be unrecorded, never called synthetic. `tests/unit/test_provenance.py` ties the wording to
  the generators: change a generator's seed, suburbs or placeholders and the table must follow.
- `scripts/check_design.py` runs Impeccable's deterministic design rules (pinned in `versions.toml`)
  on the built pages in CI. Advisory only: fix real findings; set a finding aside only in its
  `DELIBERATE` list, with the reason.
- Plain HL7 segment, field and component names live in `gateway/hl7_names.json`, shared by the
  dashboard and the inspector; they must match HL7 v2.4 and the data types in the rules file.

## Offline sandboxes
`make setup-offline` uses stub or substitute packages when packages.fhir.org is blocked. Reports
flag this (`package_substitutions`). Never publish numbers from a substituted run; CI refuses them.
