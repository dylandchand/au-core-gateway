# Interface support runbook

What to do when the lab interface misbehaves: one entry for each fault the
[Interface Monitor](https://dylandchand.github.io/au-core-gateway/monitor/) can stage, with what you
see, what the gateway answers, and the checks to work through in order. It applies to the Monitor
and to the local listener (`python -m gateway listen`). Everything here uses synthetic data only.

This file is generated by `scripts/make_runbook.py` from the faults in `gateway/monitor/build.py`,
and every reply quoted is what the gateway's own code answers. Do not edit it by hand.

## Reading an acknowledgement

Every message is answered with an HL7 acknowledgement (ACK). Its `MSA` segment carries the code
and a short reason.

| Code | Means | What to do |
| --- | --- | --- |
| `AA` | Accepted: read and checked, no errors by the gateway's own checks | Nothing, unless it carries warnings |
| `AE` | Error: read, but the gateway's checks found a problem (the reason names the first, and its HL7 field) | Follow the fault's entry below |
| `AR` | Rejected: unreadable, not UTF-8, or a message type this interface does not handle | Check the sender's set-up |
| no ACK | Nothing complete arrived | Check the connection (see the network faults) |

An `AA` means received and read, not that every value is right: the official AU Core validator runs
separately (see "Accepted, but still wrong").

Field locations read as HL7 does: `PID-3` is field 3 of the patient line, `OBX(2)-5` is field 5 of
the second result line.

## First checks, for any incident

1. **Is anything arriving?** Check when the last message came in (the Monitor's "Last message", or
   the listener's log).
2. **One sender or all of them?** One points at that system; all points at the network or the
   gateway.
3. **What did the gateway answer?** Read the ACK code and reason, and find the field it names.
4. **Is it waiting?** A lab report for a patient not registered yet is held, and filed by itself when
   the registration arrives (queue limit: 500).
5. **Was it sent twice?** A resend of the same message is answered as a duplicate and processed
   once (the gateway remembers the last 20,000 messages).
6. **Record it.** Log the incident with the control IDs (`MSH-10`) affected, what you saw and what
   you did.

Escalate early when results for patients are delayed. Problems in the data are fixed at the source:
raise them with the sending lab, never patch them in the gateway.

## Problems in a message

### Lab report for an unknown patient

A lab report arrives for a patient the hospital has no registration for, and none follows. The gateway holds it, and it stays waiting.

**Where to look:** PID-3 matches no registered patient.

**The gateway answers:**

- `AE` Held: Results for an unregistered patient at PID-3

**Checks, in order:**

1. Read the error: the identifiers in PID-3 match no registered patient.
2. Check the held queue: the report waits there, and is filed by itself if the registration turns up (see 'Lab report before its registration').
3. If it waits too long, check whether that patient's registration failed earlier, and confirm the identifiers with the sending lab.
4. Never file the results against a best guess. Log an incident and keep the report held until the patient is confirmed.

### Lab report before its registration

A lab report arrives first and its patient's registration a few seconds later, as happens when two systems send at once.

**Where to look:** PID-3 matches nobody yet.

**The gateway answers:**

- The report: `AE` Held: Results for an unregistered patient at PID-3
- Its registration: `AA` Accepted
- Then the held report is filed: `AA` Accepted (no second acknowledgement)

**Checks, in order:**

1. The report gets AE (no registered patient) and is held, not thrown away.
2. When the registration is accepted, the gateway retries the held report and files it.
3. Check the filed report: it is checked again on filing, so any other problem in it still shows.
4. If reports are often held, ask why registrations arrive late: the two systems may send on different schedules.

### Resent after a lost acknowledgement

The gateway answers a lab report, but the acknowledgement is lost on the way back, so the sender sends the same message again.

**Where to look:** Same MSH-10, same content.

**The gateway answers:**

- The first copy: `AA` Accepted
- The second copy: `AA` Duplicate of message 6; not processed again

**Checks, in order:**

1. The second copy has the same sender (MSH-3, MSH-4), control ID (MSH-10) and content: the gateway answers it with the original's code and processes nothing twice.
2. Check the log: the resend is marked as a duplicate of the first message.
3. If resends are frequent, the acknowledgements are not getting back: check the sender's timeout and the network between the two systems.
4. A control ID reused for a different message is not a duplicate: it is processed, with a warning at MSH-10, and the sender's numbering should be fixed.

### Result with a decimal comma

One numeric result arrives as 5,4 instead of 5.4.

**Where to look:** OBX-5 arrives as 5,4.

**The gateway answers:**

- `AE` Numeric result is not a number at OBX(2)-5

**Checks, in order:**

1. Read the error: it names the result and the field (OBX-5, the result value).
2. Ask what changed: a decimal comma usually means a regional setting changed on the sending system.
3. Contact the lab's interface team with the message's control ID.
4. The result was not converted, so nothing wrong reached the record. Log the incident and note the sender's change for change management.

### Mistyped test code

A result's LOINC test code has a mistyped last digit.

**Where to look:** OBX-3 check digit is wrong.

**The gateway answers:**

- `AE` LOINC code is not valid at OBX(1)-3

**Checks, in order:**

1. Read the error: the LOINC check digit in OBX-3 does not match the code.
2. Compare the code with the lab's test catalogue; a typo in the sender's code table is the usual cause.
3. Raise it with the lab so the table is corrected at the source, not patched here.

### Unknown result status

A result arrives with a status code that is not in the agreed rules.

**Where to look:** OBX-11 is not in the rules.

**The gateway answers:**

- `AE` Code with no mapping at OBX(1)-11

**Checks, in order:**

1. Read the error: the status in OBX-11 is not in this lab's translation rules.
2. Check it against HL7 table 0085 (observation result status).
3. If the lab has started sending a legitimate new status, update the rules through the change process. If not, ask the lab to fix it.

### Unsupported message type

The sender starts sending discharge messages (ADT^A03), which this interface was never set up for.

**Where to look:** MSH-9 is ADT^A03.

**The gateway answers:**

- `AR` Message type not handled at MSH-9

**Checks, in order:**

1. Read the rejection (AR): the message type is not one this interface accepts.
2. Check the interface agreement: which message types should this sender send?
3. Either the sender filters them out, or supporting them goes through a change request.

### Accepted, but still wrong

A registration whose IHI has one wrong digit. The gateway's own checks accept it; HL7's official validator, which runs separately, rejects the IHI check digit.

**Where to look:** PID-3 IHI check digit is wrong.

**The gateway answers:**

- `AA` Accepted

**Checks, in order:**

1. An ACK of AA means the message was received and read, not that every value is right.
2. Official validation runs as a separate step (see the Results page), and that is where this one is caught.
3. Trace it to PID-3 and ask the sender to correct the IHI at the source.

## Problems on the network

### Sender cannot reach the gateway (simulated on the Monitor)

Simulated: the sending system is pointed at the wrong address or port, so nothing arrives and nothing is acknowledged.

**Where to look:** Nothing arrives, nothing is acknowledged.

**The gateway answers:**

- Nothing: no complete message reaches the gateway, so no acknowledgement is sent.

**Checks, in order:**

1. One sender or all of them? One points at that system; all points at the network or the gateway.
2. Is the gateway listening? Check the service is running on the expected port.
3. Can the sender reach it? Check the address, the port, recent DNS or firewall changes.
4. The sender will be queueing messages. Once fixed, watch the backlog drain and check nothing was lost.
5. Log an incident; escalate early if results for patients are delayed.

### Connection drops mid-message (simulated on the Monitor)

Simulated: the connection breaks before the end-of-message marker, so the gateway never sees a complete message and sends no acknowledgement.

**Where to look:** The end-of-message marker never arrives.

**The gateway answers:**

- Nothing: no complete message reaches the gateway, so no acknowledgement is sent.

**Checks, in order:**

1. The sender times out waiting for the ACK and usually resends.
2. Check for repeats: a resent message carries the same control ID (MSH-10).
3. If drops keep happening, look at the network between the two systems.
4. Log it, with the control IDs affected.

## Useful commands

```sh
python -m gateway listen --state out/interface-state.json   # waits on 127.0.0.1:2575; keeps what it knows across restarts
python -m gateway send fixtures/golden                      # sends files, prints each MSA line
```

The state file is JSON: `registered` (accepted registrations), `held` (lab reports waiting for their
patient, with `held_since`) and `seen` (the messages already answered, for spotting resends).

## Recording an incident

- When it started, and when it was noticed
- Which sender, and the control IDs (`MSH-10`) affected
- The ACK codes and reasons the gateway sent
- What was checked, what was found, and who was contacted
- How it was resolved, and whether anything needs a change request
